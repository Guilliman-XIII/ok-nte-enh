## 0. 执行结论

当前第一队自动战斗应判定为 **No-Go**，暂不继续消耗深渊次数，也不应把
`d29c52d` 重新加载后直接投入下一场实战。

这不是简单的数值或延迟微调问题，而是两个基础动作模型没有成立：

1. 白藏的三条主要输出路径都只发送右键，没有持续普攻输入。用户观察到的“一直闪避不攻击”
   是代码的直接结果，不是偶发识别误差。
2. 早雾开场 E 被通用技能 helper 判定为成功后，约 13 ms 就进入切人决策；日志同时记录
   `animated=False`。路线完成只证明“按键被接受或图标变暗”，不证明长按 E 已完成聚怪。
3. 第二次实机在白藏大招后约 84 秒内发生 45 次 Planner 切人，其中白藏与早雾互切各 20 次。
   这是明确的调度振荡，不是可接受的轮转。
4. 两段 NVIDIA 录像写入的是纯黑帧，不能承担视觉验收。当前只能证明脚本发送过输入，不能证明
   技能、命中、增益或伤害真实发生。

下一步不应继续堆补丁。正确顺序是：

```text
修复录屏证据链
-> 手动校准白藏和早雾的真实动作
-> 实现单角色可验证动作
-> 恢复第一队轮转
-> 增加双队命名预设
-> 验证第二队
-> 最后进入高层深渊
```

白藏当前最值得验证的自动输出候选是
`点按左键第一段 -> 长按左键强化攻击 -> 条件 E -> Q 后继续站场`。连续右键只能保留为实验备选，
不得继续作为默认输出。

| --- | --- | --- |
| `L0-HARD` | 本地代码、Git 对象、日志、录像码流或软件日志直接证明 | 白藏只调用右键；早雾 13 ms 后切人；录像为纯黑帧 |

## 3. 根因审计

### 3.1 P0：白藏行为模型错误

当前 `src/char/Baicang.py` 存在一条闭环错误链：

1. 白藏关闭了 Planner 的通用普通攻击站场兜底。
2. Q 后爆发、E 后补偿和无技能 fallback 最终都进入 `_checkpointed_dodge()`。
3. `_checkpointed_dodge()` 只反复调用 `_right_click_burst()`。
4. `_right_click_burst()` 只调用 `self.click(..., key="right")`。
5. 动作返回 `True` 后，Planner 将其当作已成功的 `DAMAGE/default_action`，不会再补通用平 A。

`DAMAGE` 是 Planner 元数据，不会把右键闪避自动变成攻击。当前代码没有表达“闪避后追击”的复合动作，
只表达了“持续向某个方向移动并连点右键”。声音触发器又会在这个循环中继续请求闪避，使视觉表现进一步
偏向连续闪避。

此前 `docs/research/baicang.md` 已注明外部机制未经实机验证，却没有保存直接 URL，随后仍把
“闪避后右键触发追击”提升为默认实现。这是研究结论进入生产代码时缺少证据门槛造成的流程问题。

### 3.2 P0：早雾动作完成语义错误

当前早雾使用通用 `click_skill_action(down_time=0.25)`：

- 默认不要求技能动画；
- 技能按下后可能自动补左键；
- 图标变暗即可返回成功；
- `post_sleep=0`；
- strict route 切人会跳过通常的切人等待保护。

公开技能文本指向的聚怪动作是长按 E，而不是“按住约 0.25 秒、图标一暗就切走”。公开资料没有给出
长按阈值、咬地完成帧或可安全取消帧，所以现在既不能证明 0.25 秒足够，也不能凭感觉改成另一个固定值。

早雾需要角色专属动作：成功必须至少表示“长按形态已进入且动作到达不可取消点”，理想情况下还应观察
到吸附/浮空效果。这个等待应局部属于早雾，不能全局拖慢 strict route；第二队的环合切人仍可能需要快切。

### 3.3 P1：动作成功只有输入语义，没有效果语义

当前日志已经能区分 `clicked` 与 `animated`，但 strict route 最终仍把 helper 的布尔返回值当成步骤完成。
后续实现需要在概念上区分：

```text
PRESSED   按键已发送
ACCEPTED  CD/图标/动画表明游戏接受了输入
COMMITTED 动作已到达切人不会取消的承诺点
EFFECTIVE 聚怪、增益、环合、资源或命中效果已出现
```

第一阶段不应立即创建全局新框架。先给早雾和白藏写局部、可测试的专属动作；当至少两个独立角色都需要
同一套完成等级时，再把它提炼为 Planner 公共结果类型。这符合最小实体原则，也能避免为未验证机制设计
过度抽象。

### 3.4 P1：现有测试验证错了层级

现有测试主要验证：

- 动作对象能被 Planner 选择；
- 模拟 `click_skill()` 返回 `True`；
- route 能走到下一步；
- 发生过鼠标调用；
- 测试中的 `sleep` 被替换为空操作。

它们没有验证：

- 左键和右键的真实顺序；
- 长按达到阈值后才松键；
- 切人发生在不可取消点之后；
- 单位时间内存在有效普攻；
- 动作被声音抢占后会安全释放所有按键；
- 视觉效果或资源状态真实出现。

因此测试通过与实机失败并不矛盾。后续必须增加行为级输入轨迹测试和实机证据门槛。

## 4. 公开机制复核

### 4.1 白藏

当前公开资料形成以下待验证候选：

- 普攻最多五段；在特定普攻段后长按普攻可触发强化攻击并射出延迟爆炸的咒令。
- 静止长按闪避和移动中长按闪避会进入不同强化动作，说明移动键残留会改变结果。
- E 在强化普攻后、闪避后存在不同派生，不适合无条件按冷却释放。
- 普攻与言灵字相关；Q 开启领域后仍需要白藏继续站场输出。

主要来源为开放编辑的 [BWIKI 白藏技能页](https://wiki.biligame.com/yh/%E7%99%BD%E8%97%8F)，并与
[TapTap 公测攻略](https://www.taptap.cn/moment/798266191830321018) 交叉阅读。

它与当前 BWIKI 在部分普攻触发描述上并不一致，不能用于确认当前版本输入序列。

仍然未知：

- 长按普攻和长按闪避的最短稳定时长；
- 三枚咒令发射后何时可稳定衔接 E；
- 当前公测版本中不同 E 派生对应的言灵字；
- 纯长按闪避与普攻派生的真实 10 秒输出差异；
- Q 的最佳资源门槛和真实有效站场时间。

不同测试版本资料对 E 派生与言灵字映射存在冲突，不能把旧测试期资料直接编码进当前脚本。

## 5. 第一队新版设计

目标阵容默认使用白藏 + 达芙蒂尔 + 早雾 + 哈妮娅竞速版。第 2 天设置明确生存决策门槛；如果中层
实机出现死亡、持续危险血线或需要人工救场，则第 3 天插入最小法蒂娅生存预设，而不是把生存问题留到
最后一天。首版由用户显式选择竞速/生存预设，不伪装成自动血线识别。

### 5.1 白藏候选动作

按以下优先级实测：

| 模式 | 输入候选 | 定位 |
| --- | --- | --- |
| `normal_baseline` | 连续左键普攻，短间隔检查声音/死亡/切人 | 必须先成立的保守基线 |
| `a1_hold_a` | 释放移动键 -> 点按左键第一段 -> 长按左键 -> 等咒令射出 | 首选强化候选 |
| `a1_hold_a_e` | `a1_hold_a` 成功后，E 可用才释放 E | 条件派生候选 |
| `single_dodge_variant` | 释放移动键 -> 单次长按右键 -> 等咒令射出 -> 条件 E | 实验备选 |

明确禁止：

- 连续无条件右键；
- 方向键长期按住后连点右键；
- 前一次强化动作未确认完成就发送下一次闪避；
- 因 `DAMAGE` 标签而假定动作造成了伤害；
- Q 后立即让普通 Planner 把白藏切走。

初版生产逻辑应使用 `normal_baseline`，同时通过配置选择一个强化候选做 A/B 实测。任何长按都必须用
`try/finally` 释放鼠标和移动键，并保留 0.1-0.2 秒级的声音中断检查点。

### 5.2 早雾候选动作

多目标模式：

```text
释放移动键
-> 面向怪群
-> 按住 E 到实测阈值
-> 松开 E
-> 等待吸附与咬地
-> 到达实测不可取消点
-> Q 可用且收益成立时释放 Q
-> 确认 Q 动画/增益
-> 切下一名角色
```

Boss 模式在没有稳定场景识别前必须由显式配置选择。首版不假装能自动识别 Boss；暂定跳过无意义的
浮空等待，仅在实测证明 Q 增益值得时让早雾入场。

### 5.3 队伍状态机

| 状态 | 入口 | 核心动作 | 退出条件 | 失败出口 |
| --- | --- | --- | --- | --- |
| `TEAM_SYNC` | 战斗开始 | 校验活动预设、一次性武装状态与可用的四槽视觉证据 | 队伍可信 | 深渊中不可信则停止自动战斗并提示，不消耗本场 |
| `OPEN_GATHER` | 多目标且本场未执行 | 早雾专属长按 E，Q 可选 | 动作到达 `COMMITTED` | 超时直接回白藏，不重复刷 E |
| `SUPPORT_SETUP` | 聚怪完成 | 哈妮娅、达芙蒂尔的可选短切 | 已接受且达到各自动作承诺点 | 任一步失败就跳过，不锁死路线 |
| `BAICANG_PRIME` | 前置结束或超时 | 释放残留按键，进入白藏基线/强化候选，条件 E/Q | 输出循环已建立 | 候选失败降级左键基线 |
| `BAICANG_FIELD` | 白藏输出已建立 | 持续输出、声音闪避/反击可抢占 | 明确增益到期、危急生存或战斗结束 | 普通辅助评分不得频繁打断 |
| `RECOVERY` | 死亡、脱战、route 超时、动作异常 | 释放全部按键、清 route、优先回白藏 | 状态稳定 | 失败关闭队伍逻辑 |

首轮目标不是把所有辅助技能都塞进开场，而是最短时间建立白藏的有效输出。当前约 17.1 秒的前置必须
在有视觉证据后按伤害收益裁剪；任何无法证明生效的辅助步骤都应先移出强制 route。

手动预设本身只能证明“用户选择了哪份配置”，不能证明游戏画面当前就是该队伍。首阶段使用一次性
`armed_for_next_battle`：用户每次切好队后只需点一次对应预设，战斗加载后立即消费该状态。若没有本次
武装确认，也没有四槽完整视觉匹配，深渊自动战斗必须失败关闭；不能带着错误角色逻辑降级继续打。

### 5.4 第一队验收门槛

只有同时满足以下条件，第一队才从 No-Go 升级为可进入中层深渊：

1. 启动日志记录 build ID/commit，测试前确认它等于待验证提交，且脚本已完成刷新或进程重启。
2. 早雾长按 E 连续 10 次至少 9 次进入目标形态，且切人不取消聚怪。
3. 白藏基线连续 10 秒内存在稳定左键攻击，不出现连续右键刷屏或按键卡住。
4. 白藏强化候选连续 10 次至少 9 次触发预期动作，失败时能自动降级平 A。
5. 任何 3 秒窗口内不出现无路线理由的同一对角色反复互切。
6. 白藏获得一个完整、经实测确定的最小站场窗口，普通辅助评分不能打断。
7. route 超时、死亡、声音抢占和脱战后全部按键都会释放。
8. 录屏中能看到技能/命中/状态，日志时间可与画面同步。

## 6. 双队固定配置问题与方案

### 6.1 当前风险

当前数据库只有一份全局 `fixed_team`：`enabled + 4 slots`。固定队伍启用后，
`BaseCombatTask._do_load_char()` 会以置信度 1 直接构造指定角色，不再验证当前画面头像。

因此：

- 换成第二队却忘记修改固定配置时，程序可能按第一队逻辑运行；
- 当前扫描结果只是 UI 临时状态，不等于可复用阵容；
- 固定槽位严格依赖游戏栏位顺序；
- 保存固定队伍还会修改角色的全局默认出招表；
- 保存失败时 UI 可能仍提示成功。

这不是简单增加两个按钮就能完整解决的问题。首版需要便利，运行层仍要保留失败关闭边界。

### 6.2 推荐 schema v6

在现有 `fixed_team` 内扩展，不新建数据库：

```json
{
  "fixed_team": {
    "enabled": true,
    "selection_mode": "manual",
    "active_preset_id": "team_baicang_speed",
    "slots": [],
    "presets": {
      "team_baicang_speed": {
        "name": "白藏竞速队",
        "slots": []
      },
      "team_baicang_survival": {
        "name": "白藏生存队",
        "slots": []
      },
      "team_chiz": {
        "name": "小吱盈蓄队",
        "slots": []
      }
    }
  }
}
```

`slots` 保留为活动预设对当前运行 API 的兼容投影，现有加载代码先不用整体重写。它不等于旧版本数据
兼容：当前 v5 规范化只保留 `enabled + slots`，旧程序打开并保存 v6 数据会丢失全部 `presets`。
本项目选择一次性 v5 -> v6 迁移并在迁移前保留可恢复备份；迁移后禁止再用旧版保存数据库。如果必须
支持无损降级，则预设应改存独立 `team_presets.json`，不能承诺旧版认识 v6 字段。

预设中的 `combo_id` 是局部覆盖，不能反向修改角色的全局默认出招表。迁移必须覆盖：v5 -> v6 幂等、
活动投影同步、角色/出招表删除后的全部预设引用清理、原子写入失败、旧版降级限制和恢复路径。

### 6.3 两阶段交付

第一阶段先交付命名预设和一键切换：

- 从当前扫描/固定槽位保存“白藏竞速队”和“小吱盈蓄队”；触发生存门槛后再增加“白藏生存队”；
- UI 清楚显示活动预设；
- 点击预设只武装下一场战斗，加载后消费；
- 保存失败必须返回错误；
- 游戏内槽位顺序按各自预设保存，不假设两队顺序相同。
- 没有本次武装确认或完整视觉匹配时，深渊自动战斗停止并提示，不沿用上一次队伍。

第二阶段再做自动匹配：

- 八名角色都完成一次特征绑定后，在同一帧识别四个槽位；
- 只接受四人完整、唯一匹配的预设；
- 按成员集合确定队伍，再按游戏当前顺序重建有效槽位；
- 部分识别、歧义或无匹配时不得沿用上一个预设，深渊模式直接停止自动战斗并提示；
- 非深渊通用自动战斗才允许降级逐槽视觉识别，无法识别的角色使用通用 `BaseChar`；
- 战斗中不得重建正在运行的 Planner。

实施顺序是 **手动一键切换优先，自动匹配随后**。这能先满足本轮深渊期限，同时避免把模糊识别引入
强制队伍路线。

## 7. 录屏黑屏复盘与正式证据协议

### 7.1 本机证据

两段 NVIDIA 录像分别约 37 秒和 91 秒：

- 文件是有效的 1920x1080 H.264；
- 视频只有约 1 FPS、740-780 bit/s；
- 抽样帧亮度全部为 0，编码进去的就是纯黑帧；
- AAC 48 kHz / 192 kbps 立体声音轨正常。

NVIDIA Overlay 日志显示：

```text
Desktop mode: desktop
DesktopCapture Supported: true
DesktopCapture Enabled: false
captureMethod: Unknown
width/height/fps: 0
```

最可信解释是：NVIDIA 没有挂上《异环》的游戏捕获路径，退到桌面模式；桌面捕获又被关闭，因此写入
了声音和黑色画面。日志同时显示 HDR 关闭、Freestyle 未激活，所以“动态亮丽”不是本次主因；编码器也
已正常工作，改 AV1/HEVC 不会修复画面来源。

NVIDIA 官方说明窗口/无边框和桌面录制受支持，参见
[ShadowPlay 窗口模式支持](https://nvidia.custhelp.com/app/answers/detail/a_id/3324)；部分受保护内容会阻止
捕获，参见 [NVIDIA 受保护内容说明](https://nvidia.custhelp.com/app/answers/detail/a_id/5602)。

### 7.2 最低成本排查

1. 在游戏大厅按 `Alt+F1` 截图，确认截图路径是否也黑。
2. 打开 `Alt+Z -> 设置 -> 视频捕获 -> 桌面捕获`。
3. 使用 1080p、60 FPS、H.264，在大厅录制 10 秒并立即回放。
4. 若仍黑，不再消耗时间排查 NVIDIA，切换到 OBS。

正式调试推荐 OBS 管理员模式 + 窗口捕获 `HTGame.exe`；窗口捕获失败时再使用明确物理显示器的
显示器捕获。OBS 官方排障和录制建议见：

- [Game Capture Troubleshooting](https://obsproject.com/kb/game-capture-troubleshooting/)
- [Standard Recording Output Guide](https://obsproject.com/kb/standard-recording-output-guide)
- [Window Capture Sources](https://obsproject.com/kb/window-capture-sources)
- [Application Audio Capture](https://obsproject.com/kb/application-audio-capture-guide)

正式协议：

1. 每次会话先做 10 秒大厅预检，失败就禁止进入深渊测试。
2. 校准动作时优先录 120 FPS；若编码不稳定，使用 60 FPS 并接受 16.7 ms 粒度。
3. 正式通关证据使用 1080p 60 FPS、NVENC H.264、MKV，结束后再转封装 MP4。
4. 关闭 NVIDIA 即时回放，避免两个捕获程序同时挂钩。
5. 每场单独文件，名称包含队伍、关卡、轮次和开始时间。
6. 开录后保留 5 秒队伍画面并口述测试编号/时间，作为与日志的同步点。
7. 战斗期间不人工补操作，结算保留 5 秒再停止。

首次实测已经证明队伍可以进入战斗并完成切人，但输出质量未达到可用门槛。日志显示首轮执行
九原 E、零 Q/E 后，旧路线强制零留场等待第二次 E 与环合；零从 21:28:46 到 21:28:58
持续普通攻击约 12 秒，明显侵占小吱站场时间。同时，冷却中的零 Q/E 被普通 Planner 高频重复
提交，日志动作计数失真，也增加了无效操作。

该问题是队伍轴设计错误，不是通过继续延长等待或提高切人频率可以修复。结合 OKNTE 历史实现中
小吱连续三次 E 的明确动作，以及实战“主 C 应先接管、后续再重建环合”的顺序，当前实现改为：

1. 首轮只执行九原 E、零可选 Q/E，随后立即回小吱。
2. 小吱 Q 后允许最多三次 E，每次前穿插 0.5 秒普通攻击，并逐段检查当前角色、技能可用、
   死亡和脱战。
3. 小吱保持站场，第一次创生环合成熟后切九原；随后由零 E、`零 -> 翳` 延滞环合、翳 Q/E
   和可选九原 E 完成短切循环，再回小吱。
4. 零 Q/E 增加可用性门控；日志分析器把十次以上零技能重试或五次以上零站场等待判为异常。

当前第二队结论仍为：**实机 No-Go，允许进入下一轮定向复测**。下一场必须同时满足以下门槛才可
提升状态：首轮零 E 后约 3 秒内交场、小吱完成可见的主 C 输出窗口、至少两次 E 在可用时成功、
两次目标环合顺序正确，且零与翳不再长期占场。
