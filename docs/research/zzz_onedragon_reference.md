# 绝区零一条龙 (ZenlessZoneZero-OneDragon) 战斗编排参考

> 外部参考研究。来源: GitHub `OneDragon-Anything/ZenlessZoneZero-OneDragon`（及插件仓
> `ZZZ-OneDragon-Plugins`），2026-07-21 浅克隆研究。所有内容标注 [EXTERNAL]，是设计借鉴而非
> 异环事实。用户本地有此脚本（每日使用，勿改）；本研究只看 GitHub 副本。

## 它是什么路线

[EXTERNAL] 它的战斗编排**不是**实时评分大脑，也**不是**硬编码状态机，而是一套**完全数据驱动的
规则引擎**：感知层把画面/声音写成"带时间戳的状态"，决策层用 YAML 里声明的布尔表达式匹配状态，
命中就执行一串原子操作；高优先级事件（闪避/连携）可打断低优先级动作（主循环输出）。

所有"角色怎么打、何时切人、何时放大招"全写在 `config/` 的 YAML 出招表里，引擎本身不含角色逻辑。
这与 ok-nte"角色各自声明动作 + planner 评分"是两条路线，但底层抽象（状态/意图/优先级/打断）可借鉴。

## 核心机制速览

- **主循环**: 感知线程不断写状态 → 状态变更触发高优先级场景打断 → 主循环按间隔挑选命中的规则执行。
  优先级链（写在配置注释）: 闪避(97/99) > 连携(98) > 快速支援(97) > 扣血(90) > 合轴(80) > 主线程(9)。
- **切人**: 三层。①每个角色一个"速切模板"声明"我在什么状态下想上场"；②队伍级"轮换-合轴"模板按
  布尔条件（能量满/特殊技可用/BUFF 缺失/失衡期）决定切谁——本质是"谁技能好了谁上"，但判据是布尔
  条件而非数值评分；③切人物理执行按队伍位置算"切下一个/上一个"。
- **放技能/大招**: 检查"能量/技能就绪状态"（画面识别按钮高亮、能量条长度），不检查冷却计时。
  "在正确情境（失衡期/站场期）下，技能亮了就放"。另有全局兜底: 前台终结技可用且开关开启 → 自动
  注入"终结技被强制释放"状态（2 秒防重复），角色出招表接住放 Q。
- **自动闪避**: 双信号融合——YOLO 闪光分类器（视觉，红光=闪避/黄光=格挡）+ 音频模板归一化互相关
  （听觉），二者取或触发；用"闪光早于伤害 0.3 秒"的领域知识设时间窗口，触发后清空音频缓冲去重。
- **目标选择**: **不自己检测怪物坐标**，而是"按锁定键让游戏代劳 + 周期转镜头找怪 + CV 检测锁定
  状态 + OCR 读距离"。把最难的瞄准外包给游戏，极大简化战斗逻辑。
- **配置**: 三层 YAML（战斗策略入口 / 状态处理模板 ~150 个 / 操作出招表 ~400 个），状态表达式 DSL
  支持 `[状态, 时间min, 时间max]`（时间窗口）、`[状态]{值min,值max}`（数值区间）、`& | ! ()`。
  新增角色零改引擎，只加配置。

## 架构分层（解耦）

```
感知层(写状态) → 状态总线(StateRecorder: 时间戳+值) → 决策层(规则引擎, 游戏无关)
  → 执行层(原子操作序列, 可中断) → 输入层(键盘/虚拟手柄)
```

- 感知与决策完全解耦，中间只靠"状态名字符串"约定。
- 框架与游戏解耦: `conditional_operation/` 是通用规则引擎，绝区零只实现识别和原子操作。
- 并发: 多个线程池（识别/决策/执行），保证"同一时刻只有一个动作序列在跑，但高优先级可打断"。

## 对 ok-nte 的可借鉴点

1. **带时间戳的状态作为感知-决策契约**（最重要）。条件能直接写"该状态 0.3 秒内发生过"。
   启发: 我们的 planner 若把角色/全局事实建模为"带时间戳+数值的状态"，`combat_policies` 就能用
   "时间窗口 + 数值区间"表达触发条件，比纯布尔更精确，天然支持"最近发生过 X"的时序判断。
2. **优先级 + 可打断的动作模型**。priority 数值 + 中断树 + "动作不打断"无敌帧保护，优雅解决
   "闪避必须能打断输出，但无敌帧内不能被打断"。启发: 我们评分之外可引入"优先级层 + 打断规则"，
   并给动作声明"不可打断窗口"。我们已有声音闪避接管机制，方向一致。
3. **多信号融合 + 时间窗口去重的闪避**。视觉闪光 + 音频互相关取或，用预警信号早于伤害的时序差设窗口。
   启发: 我们已有 WASAPI 音频 + OpenVINO，可对照实现双通道闪避；音频用归一化互相关比能量阈值抗噪。
4. **善用游戏自带锁定，把目标选择外包给游戏**。启发: 在投入检测定位前，先评估异环的锁定/自动索敌
   能否复用（我们已有"自动目标"）。我们的视觉引导翻滚是补充（锁定只锁一只，翻滚方向朝怪群是另一回事）。
5. **声明式出招表 + 总模板顺序轮询**。与我们"角色各自声明动作、combat_plan 保持声明式"契合。
   差异: 它用"书写顺序"定优先级，我们用"评分"——评分是更优演进；但它的"兜底链"可作评分相同时的
   tie-breaker。

## 它路线的局限（我们评分路线的优势）

[EXTERNAL] "条件规则 + 书写顺序"在角色/配队爆炸时 YAML 极度膨胀（150+ 状态模板、400+ 出招表，
大量角色特判 hardcode 散落在"轮换-合轴"里，可维护性下降）。ok-nte 的"实时评分大脑"正是对这一痛点
的更好回答——把"谁该上场"从"写死的优先级链"变成"可计算的价值函数"。建议保留它的"状态契约 + 优先级
打断 + 声明式出招表"骨架，但用评分替换其"顺序轮询"内核，并警惕"角色特判散落各处"（用我们的
`describe_role()`/`combat_plan()` 内聚到角色自身来避免）。

## 闪光分类器：它怎么训的、能不能白嫖 [EXTERNAL]

> 2026-07-22 读本仓克隆的 `auto_battle_dodge_context.py`、`yolo/flash_classifier.py`、
> `docs/develop/setup/repositories.md` 得出。回答"它的视觉闪避怎么训、有没有现成数据可用"。

**模型本身**：`FlashClassifier` 是个 YOLOv8n 分类器（`Yolov8Classifier`，模型名 `yolov8n-640-flash-20250906`，
640 输入，nano 最小号）。三类：`class_idx` 0=无、1=红光（`DODGE_RED`，闪避）、2=黄光（`DODGE_YELLOW`，格挡）。
`check_dodge_flash` 对**全屏**跑模型，红/黄光直接判闪避，否则才回落到音频结果——视觉优先、音频兜底（取或）。
音频通道和本 ok-nte 同一师门：librosa + 4 阶 Butterworth 高通(1000Hz) + 归一化互相关，单模板 `template_1.wav`，
阈值 0.1，**触发后 `clear_audio()` 清缓冲去重**。

**怎么训、谁训**：不是大家一起训，是**一个组织集中维护**。背后是 `OneDragon-Anything` 组织，多仓库协作：
主仓放业务代码；专门的训练仓 `OneDragon-Anything/OneDragon-YOLO` 负责训模型，训好打包成 `<模型名>.zip`，
以 release tag `zzz_model` 发布，主仓启动时按需**下载成品**消费。训练数据不在代码里，托管在 ModelScope（魔搭，
非 git），按 `<玩法>-Dataset` 命名，闪光这份叫 **`ZZZ-FlashClassify`**（另有 SR-ObjectDet / ZZZ-LostVoidDet /
ZZZ-WitheredDomainDet）。所以普通用户完全不参与训练，就是下载成品；贡献者可提交截图，但数据集和模型由几个
核心维护者集中管。

**能不能白嫖：有现成的，但对异环没用。** 模型和数据集都能公开下载，可那是**绝区零自己的美术风格**——它的红光/
黄光长什么样由绝区零定的，和异环的红光不是一回事，直接拿过来认异环画面基本认不出。**不可迁移。**

**对 ok-nte 的结论**（用户已据此拍板，见 `docs/sound_dodge_counter_design.md` §4）：
- 训异环自己的分类器没有捷径，截图和标注必须自己在异环里攒。
- 这是"数据工程"不是"代码工程"：最贵的是收集+标注三种样本（闪避红闪/蓄力红光/无）各几百张起步，没法速成。
- 代码管线（取敌人框、和听觉取或、触发去重、接打断机制）颜色启发式和分类器**完全共用**，分类器只是换掉
  "这一下是不是预警"那一个判断函数。所以**先做颜色/时长启发式**（顺带埋"实战存图"攒训练数据），等它暴露
  分不清两种红光或太吵时，数据也攒够了，再训分类器直接替换——前面建的管线一点不浪费。
- 关键区分：敌人"蓄力红光"（持续亮、该打）和"攻击预警红光"（一闪而过、该闪）含义相反，靠**持续时长**可分。
  这正是分类器比手工颜色规则更值钱的地方，也是颜色启发式要先验证的难点。
